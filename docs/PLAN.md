# SERPIN Business Tournament — ОКОНЧАТЕЛЬНЫЙ ПЛАН

**Дедлайн: 3 августа, сдача до полудня.**
Команда 4 человека: 2 разработчика (A — данные и логика, B — интерфейсы), 2 на дизайн/питч/видео/ресёрч.
Скоуп: **полный** — всё из положения + вся спека продукта. Код генерируется агентами.

## 0. Правило, на котором держится план

Функции не режем. Режем **риск**: порядок сборки такой, что демо-путь работает до того, как начинается ширина.

```
Т0  29 июля, вечер  — контракт, репозиторий, схема БД, деплой
Т1  30 июля         — ЯДРО: клиент ↔ касса ↔ CRM в реальном времени
Т2  31 июля         — акции, сегменты, аналитика, рекомендации
Т3  1 августа       — вся остальная ширина продукта
Т4  2 августа       — заморозка 14:00, полировка, артефакты
Т5  3 августа       — буфер, сдача
```

**Красная линия: 31 июля, 23:59 — путь «телефон → касса → CRM → акция → аналитика» проходится без ошибок.** Если не проходится, 1 августа не начинаем новые модули, а чиним ядро. Это единственное место, где план допускает сокращение — и только по факту, не заранее.

## 1. Продукт

**«Qadam»** — единая платформа для малого офлайн-бизнеса.

> Предприниматель без программиста и маркетолога создаёт сайт, запускает бонусную программу, собирает клиентскую базу, создаёт акции и видит их эффективность. Клиент регистрируется один раз и получает универсальный QR, работающий во всех подключённых заведениях — при этом бонусы и история каждого бизнеса хранятся отдельно.

Три вещи, которые делают это не «ещё одним лендингом»:

1. **Универсальный QR клиента** — один аккаунт на всю сеть заведений. Сетевой эффект: каждый бизнес приводит клиентов, каждый клиент делает платформу ценнее для следующего бизнеса.
2. **Активность от личной частоты визитов.** Не «мало ходит», а «этот человек обычно раз в 7 дней, прошло 14 — под риском ухода». Для ремонта телефонов та же формула даёт медиану 90+ дней и растягивает пороги сама — система адаптируется под нишу без настройки.
3. **Симулятор эффекта акции до запуска** + **воронка результата после**. Владелец видит прогноз выручки прежде, чем потратил деньги, и реальный результат — `120 получили → 76 открыли → 28 пришли → 21 использовал → 147 000 ₸` — вместо «отправлено 120 сообщений».

## 2. Архитектура

```
Next.js 15 App Router · TypeScript · Tailwind · shadcn/ui
Supabase (Postgres + Realtime)
Recharts · qrcode.react · @tanstack/react-table · Zustand (только UI-состояние)
/api/ai/*  →  @anthropic-ai/sdk, claude-opus-5 ($5 / $25 за 1M токенов), фолбэк на шаблоны
Vercel
```

**Границы ответственности слоёв — соблюдать строго, иначе агенты будут переписывать друг друга:**

| Слой | Кто владеет | Правило |
|---|---|---|
| `/supabase/**` (миграции, seed) | A | B не трогает |
| `/src/lib/**` (типы, repo, engine) | A | B только читает |
| `/src/app/api/**` | A | |
| `/src/app/(*)/**` (страницы) | B | A не трогает |
| `/src/components/**` | B | |
| `/src/lib/types.ts` | **общий** | Меняется только совместно, коммит с префиксом `contract:` |

**Политика AI:** вся логика, влияющая на цифры — уровни, активность, сегменты, рекомендации, симулятор, прогноз визита — детерминированные правила в `/src/lib/engine/`. LLM только пишет тексты (акции, рассылки, объяснение аналитики). Ключ в `ANTHROPIC_API_KEY`, только на сервере, только в route handler. Нет ключа, ошибка или таймаут → шаблон из БД, пользователь не замечает. Демо не может упасть из-за AI.

**Авторизация:** демо-режим (выбор бизнеса, короткий код). Настоящий auth — полдня, которых нет, и жюри его не оценивает. RLS не включаем, изоляция бизнеса на уровне запросов. В техописании пишем прямо: «в MVP фильтрация на уровне приложения, в продакшене — RLS-политики Postgres». Это плюс к пониманию масштабирования, не минус.

**Ключевая деталь, потерять которую нельзя:** `customer` — глобальная таблица, `membership` — пара бизнес×клиент. Один человек, один QR, отдельные балансы и история в каждом заведении. Это вся архитектурная суть продукта, и именно её показываем в финале видео.

**Seed должен быть щедрым**, иначе аналитика выглядит пустой: 5 бизнесов разных ниш, 30 инструментов по 5 категориям, 20 шаблонов акций, 120 клиентов, 6 месяцев транзакций с реалистичной сезонностью и разной частотой визитов (чтобы движок активности показал все 4 состояния).

## 4. Движок (`/src/lib/engine/`, чистые функции, покрыты тестами)

```ts
// АКТИВНОСТЬ — от личной частоты, не от абсолютных чисел
medianInterval(visits): number
activity(m): 'active' | 'declining' | 'at_risk' | 'lapsed'
   active     daysSince <= median * 1.3
   declining  daysSince <= median * 2
   at_risk    daysSince <= median * 3.5
   lapsed     иначе
// Проверка на примере из спеки: median 7 → 10 снижается, 14 риск, 25 давно не приходил ✓

// УРОВЕНЬ — по визитам, сроку жизни и сумме
level(m): 'new' | 'returning' | 'regular' | 'loyal'

// СЕГМЕНТЫ — все 13 из спеки
segments = [новые, вернувшиеся, постоянные, лояльные, давно не приходили,
            под риском ухода, много бонусов, бонусы скоро сгорят,
            часто используют акции, покупают определённый товар,
            высокий средний чек, давно не записывались, скоро день рождения]

// ПРОГНОЗ ВИЗИТА
visitProbability(m, days): number      // «Арман обычно по пятницам — 72% за 5 дней»

// СИМУЛЯТОР АКЦИИ (до запуска)
forecast(promo, segment, history): { newCustomers, returns, revenue, roi, breakEvenDiscount }

// РЕКОМЕНДАЦИИ — правила, не LLM
recommend(business, stats): Recommendation[]
   «42 клиента не приходили дольше обычного → создайте предложение на повторное посещение»
   «У 18 клиентов бонусы сгорят через 7 дней → отправьте напоминание»
   «Скидка 10% сработала лучше бесплатного сиропа»
   «По вторникам меньше всего посещений → двойные бонусы по вторникам»

// ЗАЩИТА
rotateQr(customer)                     // токен обновляется раз в 45 секунд
requireConfirm(redeemAmount)           // крупное списание — подтверждение клиентом
antiSpam(business, customer, channel)  // частотный лимит на рассылки
```

## 6. Как работать агентами (это и есть источник скорости)

**Правило один:** агент получает контракт, а не пожелание. Перед запуском модуля в промпте должны быть: типы из `types.ts`, сигнатуры repo, список экранов, критерии приёмки. Без этого агент выдумает свою модель данных, и вы потратите на интеграцию больше, чем сэкономили.

**Правило два:** один агент — один модуль — одна ветка — своя директория. Пересечение по файлам = конфликт, который никакая скорость генерации не окупает. Границы владения в §2.

**Правило три:** ничего не мержится без ревью. Агент-ревьюер дешевле, чем отладка на видео.

Готовые команды, которые стоит гонять:

```bash
/ecc:orch-add-feature   # модуль целиком: research → plan → TDD → review
```
```bash
/ecc:react-review       # ревью экранов (hooks, ре-рендеры, серверные/клиентские границы)
```
```bash
/ecc:database-reviewer  # схема, индексы, запросы Supabase
```
```bash
/ecc:security-scan      # перед деплоем: ключи, env, утечки в клиент
```

**Порядок на каждый модуль:** контракт → агент генерит → `npm run build` зелёный → ревью → мерж → руками прокликать. Пятый шаг не пропускать: агент не видит, что кнопка «Активировать» не нажимается на мобильном.

## 10. Питч, 7 слайдов

1. **Проблема** — цифры по рынку + цитаты из интервью с реальными точками
2. **Решение** — «инструменты крупных сетей в доступном формате»
3. **ЦА** — 4 сегмента из положения
4. **Ключевые функции** — сайт, лояльность, CRM, акции, аналитика, рекомендации

7. **Дорожная карта** — этап 2 (Telegram Mini App, интеграции с кассами, реальные рассылки), этап 3 (прогнозы, умные акции, депозиты и абонементы)
